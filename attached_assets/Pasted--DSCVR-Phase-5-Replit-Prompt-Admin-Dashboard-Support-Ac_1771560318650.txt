## STEP 2 — Session: support mode

Add to express-session types:
```typescript
declare module "express-session" {
  interface SessionData {
    userId: string;
    supportTargetUserId?: string;  // set when admin is in support mode
  }
}
```

When `req.session.supportTargetUserId` is set, API routes that read user data (vault, timeline, alerts, properties) should use `supportTargetUserId` as the effective user — **but only for GET requests**. All write operations (POST, PATCH, DELETE) must always use `req.session.userId` and must reject if in support mode.

## STEP 3 — API routes (`server/routes.ts`)

### Support access — user-facing (requireAuth)

```
GET /api/support-access
→ Returns current user's support grant status
→ { isGranted: boolean, grantedAt: string | null, lastAccessedAt: string | null, lastAccessedBy: string | null }

POST /api/support-access/grant
→ Creates or reactivates a support_access_grant for the current user
→ Returns { ok: true, grantedAt }

POST /api/support-access/revoke
→ Sets isActive: false, revokedAt: now on user's grant
→ If admin is currently in a support session for this user, that session is invalidated
→ Returns { ok: true }
```

### Support access — admin-facing (requireAuth + requireAdmin)

```
POST /api/admin/support/enter/:userId
→ Validates: target user has an active support_access_grant
→ If no grant: return 403 { message: "User has not granted support access" }
→ Sets req.session.supportTargetUserId = userId
→ Logs to admin_access_log: action "support_session_start"
→ Updates support_access_grants.lastAccessedAt + lastAccessedBy
→ Returns { ok: true, targetUser: { email, id } }

POST /api/admin/support/exit
→ Clears req.session.supportTargetUserId
→ Logs to admin_access_log: action "support_session_end"
→ Returns { ok: true }

GET /api/admin/support/status
→ Returns whether admin is currently in a support session
→ { inSupportMode: boolean, targetUser?: { id, email } }
```

### Admin user management (requireAuth + requireAdmin)

```
GET /api/admin/users
→ Returns all users with:
  { id, email, createdAt, lastLogin, isAdmin, isPro, proGrantedAt,
    propertyCount, hasSupportGrant }
→ propertyCount: count of active properties
→ hasSupportGrant: whether they have an active support_access_grants row
→ NEVER returns vault data, document data, or property details

PATCH /api/admin/users/:id/pro
→ Body: { isPro: boolean }
→ Updates isPro, sets proGrantedAt / clears it, sets proGrantedBy
→ Logs to admin_access_log
→ Returns updated user fields only

PATCH /api/admin/users/:id/admin
→ Body: { isAdmin: boolean }
→ Updates isAdmin flag
→ Logs to admin_access_log
→ Returns updated user fields only

GET /api/admin/users/:id/properties
→ requireAdmin only
→ Returns ONLY: [ { id, propertyName, regency, createdAt } ]
→ NO vault data, NO document data, NO compliance status
→ This is purely for support context — "which villa are we talking about"

GET /api/admin/access-log
→ Returns last 100 admin_access_log entries, newest first
→ Joined with admin email + target user email for display
```

### Modify existing data routes to respect support mode

Update these routes to check `req.session.supportTargetUserId`:

```typescript
// Helper — get effective userId, respecting support mode
function getEffectiveUserId(req: Request): string {
  return req.session.supportTargetUserId || req.session.userId!;
}

// IMPORTANT: Block writes in support mode
function blockSupportModeWrites(req: Request, res: Response, next: NextFunction) {
  if (req.session.supportTargetUserId) {
    return res.status(403).json({ message: "Cannot modify data in support mode" });
  }
  next();
}
```

Apply `getEffectiveUserId()` to:
- `GET /api/vault` — uses effective userId's properties
- `GET /api/vault/summary` — same
- `GET /api/timeline` (if it has an API route)
- `GET /api/alerts` (if it has an API route)
- `GET /api/properties` — returns effective user's properties

Apply `blockSupportModeWrites` middleware to ALL POST/PATCH/DELETE routes for vault, properties, alerts.

## STEP 4 — Support mode context (`client/src/hooks/useSupportMode.ts`)

```typescript
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";

export function useSupportMode() {
  const queryClient = useQueryClient();

  const { data: status } = useQuery({
    queryKey: ["/api/admin/support/status"],
    refetchInterval: 30000, // poll every 30s
  });

  const exitMutation = useMutation({
    mutationFn: () => fetch("/api/admin/support/exit", { method: "POST" }).then(r => r.json()),
    onSuccess: () => {
      // Invalidate all data queries so they reload as admin
      queryClient.invalidateQueries();
    },
  });

  return {
    inSupportMode: status?.inSupportMode ?? false,
    targetUser: status?.targetUser ?? null,
    exit: exitMutation.mutate,
  };
}
```

## CONSTRAINTS

1. **Privacy boundary is absolute** — `GET /api/admin/users` NEVER returns vault documents, document status, compliance scores, or alert data. Only: email, dates, isPro, isAdmin, property count, support grant status.

2. **Property expand** returns ONLY name + regency — not NIB, not address, not KBLI, not any document data.

3. **Support mode blocks all writes** — `blockSupportModeWrites` middleware on every POST/PATCH/DELETE for vault, properties, alerts. Return `403 { message: "Cannot modify data in support mode" }`.

4. **Support mode cannot be entered without an active grant** — `POST /api/admin/support/enter/:userId` must verify `isActive: true` in `support_access_grants` before setting session. Return `403` if no grant exists.

5. **Audit log is immutable** — `admin_access_log` table has no update or delete routes. Append only.
